# Kotlin Worksheet 0.7.0 Release Readiness

## Goal

Prepare the current 0.7.0 candidate for release by completing the roadmap's
Arrow-kt dependency validation, hardening Gradle classpath cache invalidation,
and making release metadata and verification steps internally consistent.

The release is ready only after the implementation passes the local and CI
verification gates and the exact checked commit is tagged. Publishing remains a
separate explicit operation.

## Scope

### Included

- Add a pinned Arrow-kt JVM Gradle fixture using Maven Central.
- Execute a worksheet that imports Arrow-kt APIs through the resolved runtime
  classpath and verifies representative transformations.
- Preserve existing root-project and subproject Gradle coverage.
- Invalidate completed and in-flight cache work when the refresh command runs.
- Include Gradle dependency/catalog configuration in cache fingerprints.
- Add regression tests for cache invalidation and dependency configuration
  changes.
- Update release-facing documentation and metadata for 0.7.0.
- Record completed and deferred roadmap items accurately.
- Ignore generated fixture output such as `bin/` directories.

### Excluded

- Persistent cache storage across VS Code sessions.
- Support for Android, Kotlin Multiplatform, or custom Gradle source-set
  layouts.
- A redesign of cancellation for shared in-flight requests.
- Automatic tag creation or Marketplace publishing.

## Arrow-kt Validation

The fixture will be a small Kotlin JVM Gradle project with a concrete Arrow-kt
version pinned in its dependency declaration. The dependency must resolve from
Maven Central and remain compatible with the repository's Kotlin 2.4.0 test
toolchain.

The integration test will:

1. Resolve the fixture's Gradle runtime classpath.
2. Assert that resolution succeeds and produces classpath entries.
3. Execute a worksheet importing Arrow-kt APIs.
4. Assert a deterministic result from an `Either` or `Option` transformation.

The fixture will not test unsupported project layouts. The existing multi-root
fixture remains responsible for nearest-subproject selection.

## Cache Hardening

`GradleClasspathCache` remains an in-memory cache keyed by project root,
worksheet directory, and detected Gradle command.

Refreshing a project will remove matching completed entries and detach matching
in-flight requests from the share map. Each resolution captures an invalidation
generation. A resolution may return its own result, but it may only populate
the cache if its generation is still current. This prevents a request started
before refresh from restoring stale data.

The fingerprint will cover the existing root build markers and source roots,
plus Gradle dependency and catalog configuration under the project `gradle/`
directory. Generated `.gradle` and `build` directories remain excluded.
Changes to dependency declarations, version catalogs, build logic, or relevant
source files therefore force a fresh classpath resolution.

Existing status values (`hit`, `miss`, `invalidated`, `shared`, and `disabled`)
and logging remain unchanged. A refresh does not cancel a running Gradle
process; it only guarantees that its result cannot repopulate an invalidated
cache entry.

## Documentation And Metadata

- Replace current user/development documentation references to the old 0.6.0
  VSIX with the 0.7.0 candidate where they describe the current package.
- Remove or resolve stale `Planned For 0.7.0` changelog content.
- Update production-readiness records to distinguish completed local checks
  from CI and manual checks still required.
- Mark roadmap items complete only when this implementation verifies them;
  leave unsupported Gradle layouts and other future work explicitly deferred.
- Keep historical version examples in publishing guidance clearly labeled as
  examples rather than current release instructions.

## Verification

The following checks are required before release:

- Unit tests for cache hits, invalidation, disabled mode, shared requests,
  refresh during an in-flight request, and dependency configuration changes.
- Full `pnpm check` including lint, compile, tests, and packaging.
- `pnpm test:vsix-install` against `kotlin-worksheet-0.7.0.vsix`.
- Local `pnpm test:integration`.
- Gradle cache benchmark with unchanged-run reuse and source/configuration
  invalidation.
- CI matrix success on Linux, macOS, and Windows, including isolated VSIX and
  integration tests.
- Manual verification of walkthrough, status bar, notifications, decorations,
  and automatic Gradle fallback.

The release workflow must validate the package version and matching tag before
publishing. The exact VSIX produced by validation is the one eligible for
Marketplace publication and GitHub release attachment.

## Release Sequence

1. Finish the implementation and documentation changes.
2. Run all local verification commands.
3. Review the final diff and confirm a clean release commit.
4. Push the release commit and `v0.7.0` tag.
5. Confirm CI for the tagged commit is green.
6. Manually run the protected Marketplace workflow with version `0.7.0`.
7. Confirm Marketplace and GitHub release metadata show `0.7.0`.

No release tag or Marketplace publication is performed as part of the code
implementation.
